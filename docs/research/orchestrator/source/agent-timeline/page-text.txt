When to use
Showing how an orchestrator split work across subagents and how long each part took, in a run history, a trace viewer or a debugging panel.
Replaying a finished agent run in a product demo or changelog, with real numbers for time, tokens and cost.
Following a multi-agent run live as events stream in from your backend.
When not to use
Use agent-orchestrator for a full screen of agent lanes with streaming text and messages; this timeline is the compact, reusable view of timing.
Use observability-trace for distributed request tracing across services rather than agents.
Use agent-run or research-run when people need the agent's steps, sources and answer, not the timing.
Use tool-call for the detail of a single tool invocation, and agent-status for one agent's current state.

API reference
AgentTimeline

A compact timeline of one orchestrated agent run. Each row is an agent with a color dot, its name and its model with the provider mark, the orchestrator on top. Spans on a shared time axis show thinking (a tint of the agent color), tool calls (solid) and waiting (hatched), and thin elbow connectors show work handed to a subagent and results coming back, with a dot where they meet the orchestrator. The run replays live: a playhead sweeps, the active span grows with a square leading edge and a short shine, connectors draw in as handoffs happen, and the header counts elapsed time, tokens and cost until it settles into a summary such as "5 agents · 26.4s · 1.5x faster than sequential · $0.16". Hover or focus a span for a card with what it did, its tool, duration, tokens and handoffs; click to pin it and dim everything off its handoff path. A failed tool call turns into a cross with a Failed label when it ends, and its retry shows a retry icon. Play, pause, restart, a speed control and scrubbing along the axis drive the replay; passing a finished run renders it complete, and live mode follows a run in progress.

Prop
Type
Default
Description
run
AgentTimelineRun
sampleRun
The run: { title?, agents, spans, handoffs?, duration?, startedAt? }. Rows follow agents in order and the first agent is the orchestrator. Defaults to a sample incident investigation with five agents, a failed query and a retry.
agents
AgentTimelineAgent[]
–
Overrides run.agents. Each agent is { id, name, model?, role?, color?, mark?, price? }. color defaults to neutral for the first agent and --series-1 to --series-4 after it; mark is inferred from the model name for Claude, GPT and Gemini; price is a blended USD rate per million tokens used for cost.
spans
AgentTimelineSpan[]
–
Overrides run.spans. Each span is { id?, agentId, kind: "thinking" | "tool" | "waiting", start, end?, label, detail?, tool?, tokens?, cost?, status?: "ok" | "failed", retry? } with times in seconds from the start of the run. tool is a name (GitHub, Web search, PostgreSQL and Notion have built-in marks) or { name, mark }. Leave end out while a span is open in a live run.
handoffs
AgentTimelineHandoff[]
–
Overrides run.handoffs. Each handoff is { from, to, at, label? }. The connector shape is inferred: a dispatch drops from the source at `at` and enters the target's next span, a result leaves the end of the source's last span and rises into the target.

Accessibility
The root is a labelled section. Each row of spans is a group named by its agent label, and every span is a button whose name reads the agent, the kind, the tool, failure, what it did, its time range and tokens; aria-pressed marks the pinned span.
Spans use a roving tab index, so the chart is one tab stop and arrow keys move between spans by row and by time.
The scrubber is a slider with a value text such as "12.4s of 26.4s" and full keyboard support; dragging anywhere on the axis moves it.
Status is never color alone: a failed call shows a cross icon and the word Failed in its card and the legend, a retry shows a retry icon and its note, and the finished state shows a check with the summary.
A polite live region announces replay, pause and the finished summary. The counting status line is not live, so it never floods a screen reader.
The span card repeats what the span's accessible name already says, so it is hidden from assistive technology.
Pointer focus draws no ring; keyboard focus shows Arc's shared focus ring on spans, the scrubber thumb and the controls.
Motion
Bars and the playhead read one CSS variable for the current time, updated every animation frame, so spans grow smoothly without React rendering per frame; React updates counters and states about twenty times a second.
An active span has a square, solid leading edge and a short shine that stops when it ends; its corner rounds off as it completes. A failed call changes to its failed look with a quick color fade when it returns.
Connectors draw in with a clip reveal from the side the handoff leaves, about 360ms, and the port dot pops in at the start of a dispatch or after a result lands.
The span card glides between spans on the morph spring, crossfades its content and springs to its new height; the status line and play button swap with one minimal crossfade.
When the run ends the playhead fades out and the status settles into the summary.
Reduced motion starts on the finished run and drops the shine, the connector draw, the card glide and the status crossfades. Playback still works when the person asks for it.
Responsive behavior
Fills its container up to the canvas width. Below a 520px container the label column narrows to dot and name, and the model moves into the span card.
When the plot would be narrower than 300px it scrolls horizontally inside its own frame with the agent labels pinned, and the replay keeps the playhead in view unless the person has just scrolled.
The status line wraps after a separator, never before, and the counters reserve the width of their final value, so the header never shifts while it counts.
Hover cards are anchored inside the component and flip below the row when there is no room above.
Performance
The run is normalized once per data change: spans sorted, connector shapes and totals memoized.
Per frame the clock writes one CSS variable; widths, the playhead and connectors are pure CSS from it. React re-renders at most about twenty times a second while playing, and memoized span buttons only update when their state changes.
The replay clock only runs while the timeline is in view, and stops when the run ends.
Handles a few hundred spans comfortably; for long traces, pass a window of the run or aggregate tiny spans.
Notes for AI

Give your coding assistant the Markdown reference instead of screenshots.

Choose it to show one orchestrated multi-agent run as a timeline: which agent did what, when, in parallel, with handoffs. It fits a card 360 to 760px wide.
Put the orchestrator first. Order subagents so connectors pass through idle rows: the agent that returns first sits right under the orchestrator, and dispatches go to the deepest row first.
Give each handoff a time that matches the spans around it: a dispatch just before the target's first span, a result just after the source's last span. The shape is inferred from those gaps.
Use kind "waiting" for an agent that is blocked on others, so parallelism and idle time read at a glance and the summary's speedup counts only real work.
Mark a failed tool call with status "failed" and a detail message, and the call that retried it with retry: true.
Real model and tool marks are built in by name; pass mark for anything else. Brand marks are sample content, never implied endorsements.
